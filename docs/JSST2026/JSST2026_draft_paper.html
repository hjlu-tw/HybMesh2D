Platform for the UNICONES CFD Solver: A Vibe Coding Approach

Abstract

High-fidelity CFD solvers often present significant usability barriers due to their complex, multi-step workflows involving geometry preparation, mesh generation, solver execution, and post-processing. This paper presents the development of HybMesh2D, an integrated graphical platform that wraps the entire simulation pipeline around the UNICONES solver — a CESE-method-based compressible flow solver. A distinctive feature of this work is the development methodology: the platform was built through vibe coding, an emerging AI-assisted programming paradigm where domain experts describe their intent to a large language model (LLM) and collaboratively produce working software. The resulting system comprises over 18,000 lines of Python (PyQt6 GUI) and 3,000 lines of C++ (mesh generation core), developed in an estimated 25 person-hours — a fraction of conventional development time. We describe the system architecture, the human–AI collaboration workflow, and demonstrate the platform's capability through a complete NACA 0012 airfoil simulation from geometry import through to flow-field visualization.

Keywords: CFD, hybrid mesh generation, AI-assisted development, vibe coding, pre/post-processing, CESE method, user-friendly simulation

1. Introduction

Computational Fluid Dynamics (CFD) has become an indispensable tool in aerospace, mechanical, and environmental engineering. However, the practical use of a CFD solver is seldom limited to the solver itself — a complete simulation workflow typically involves (1) geometry preparation and surface discretization, (2) volume mesh generation with boundary-layer resolution, (3) solver configuration and execution, and (4) post-processing and visualization of results. Each of these steps often requires separate software tools, manual file conversions, and substantial expertise in both numerical methods and software operation.

UNICONES is a compressible Euler/Navier–Stokes solver based on the Conservation Element and Solution Element (CESE) method [1], developed at the National Center for High-performance Computing (NCHC), Taiwan. While the solver kernel is mature and validated, its operational workflow remains command-line-driven and relies on a chain of preprocessing utilities (format converters, mesh partitioners) that require expert knowledge. This creates a significant barrier for new users, students, and researchers who wish to leverage the CESE method but lack the operational expertise.

To address this challenge, we developed HybMesh2D: an integrated graphical platform that unifies the complete simulation pipeline — from geometry import through flow-field visualization — into a single, cohesive application. A unique aspect of this work is the development methodology employed: vibe coding [2], an emerging paradigm of AI-assisted software development where domain experts articulate their requirements in natural language, and a large language model (LLM) generates the corresponding source code. The human expert retains full responsibility for architectural decisions, algorithm design, and physical validation, while the AI accelerates the implementation of GUI components, data parsers, and software scaffolding.

This paper makes the following contributions: (i) the design and implementation of a complete pre/post-processing platform for a CESE-based CFD solver; (ii) a documented case study of vibe coding applied to scientific software development, including quantitative observations on development efficiency; and (iii) a discussion of the applicability, benefits, and limitations of AI-assisted development in computational science.

2.1 PreProcessor Module

The PreProcessor provides an interactive geometry canvas (based on the pyqtgraph library) for loading, viewing, and resampling surface discretizations. It supports multiple spacing strategies including uniform, cosine (double-end clustering), geometric (exponential growth), and hyperbolic tangent distributions. Automatic sharp-corner detection identifies feature points where the turning angle exceeds a configurable threshold, enabling the geometry to be split into segments with independent resampling parameters. The backend is implemented as a standalone C++ executable that reads a JSON configuration and performs the resampling using cubic spline interpolation, ensuring smooth curvature preservation. The GUI communicates with the backend via a QThread worker, keeping the interface responsive.

2.2 Hybrid Mesh Generator

The core mesh generation module (C++, ~1,500 lines) produces 2D hybrid meshes comprising structured quadrilateral boundary layers and unstructured triangular far-field elements. Boundary layers are grown outward from the geometry surface using a node-marching algorithm. The generator handles convex corners through fan-element insertion (with adaptive node counts based on arc length and neighboring segment widths) and concave corners through either node merging or a thickness-diffusion blending method. A configurable number of transition layers with a separate growth rate bridges the boundary-layer region to the far-field, where the Gmsh library [3] (Frontal-Delaunay algorithm) generates unstructured triangles. The mesh module exports both VTK format for ParaView visualization and STAR-CD format (.vrt/.cel/.bnd) for solver input.

2.3 Solver Integration

The solver integration module orchestrates the execution of the UNICONES pipeline directly from the GUI. It manages three steps: (1) getPGrid, a format converter that transforms STAR-CD files into the solver's native grid format via interactive stdin input; (2) optionally, bDecompose for MPI domain decomposition; and (3) the UNICONES solver itself, running in pthread parallel mode. The solver controller (solver_ctrl.py) automatically creates a case directory structure, renames and relocates files to match the solver's expected layout, and generates the input configuration file (input.in). During execution, the worker thread parses the solver's stdout in real time, extracting iteration counts, CFL numbers, and L2 error norms for five conservation variables, which are displayed on a live convergence monitor.

2.4 Results Visualization

The results module parses Tecplot-format output files (FEBLOCK, FETRIANGLE zone type) and renders cell-centered scalar fields using an embedded matplotlib canvas. It supports both flat (tripcolor) and smooth (tricontourf via cell-to-node averaging) contour rendering, velocity streamlines (via LinearTriInterpolator sampled onto a regular grid with streamplot), and velocity vector glyphs (quiver). Users can interactively select field variables, adjust colormaps and color scale limits, and toggle mesh wireframe overlays.

3. AI-Assisted Development Methodology

The HybMesh2D platform was developed using an approach we characterize as responsible vibe coding — a mode of AI-assisted programming where a domain expert maintains full architectural control and validation responsibility, while delegating implementation to an LLM-based coding assistant. This section describes the workflow, provides concrete examples, and evaluates the development efficiency.

3.1 The Human–AI Collaboration Model

Vibe coding, as originally described by Karpathy [2], refers to a programming style where the developer "fully gives in to the vibes" and lets an AI generate code based on high-level descriptions. In our context, we adopt a more disciplined variant that distinguishes between human and AI roles:

Human (domain expert) responsibilities: defining the simulation pipeline architecture and data flow; specifying numerical algorithms (e.g., boundary-layer growth logic, corner handling strategies); designing the data format compatibility chain (STAR-CD → getPGrid → UNICONES); validating outputs against known physical solutions; and making architectural decisions (e.g., MVC pattern, command pattern for undo/redo).

AI (LLM) responsibilities: generating GUI boilerplate code (PyQt6 widgets, layouts, signal/slot connections); implementing data parsers (Tecplot FEBLOCK, STAR-CD formats); producing C++ mesh generation routines from algorithmic descriptions; creating the controller–worker–view wiring; and writing documentation.

The development proceeded iteratively: the expert described a requirement in natural language → the AI generated an implementation → the expert tested and validated → identified issues were fed back as corrections → the AI revised the code. This cycle typically converged within 2–5 iterations per feature.

3.2 Representative Development Cases

Case A: Boundary-layer generation (BoundaryLayer.cpp). The expert described the outward-marching algorithm, including the mathematical formulation of normal computation, fan-element geometry at convex corners, and the concave-node blending strategy. The AI produced the initial 610-line C++ implementation. The expert then identified edge cases: self-intersection at sharp trailing edges (resolved by adding geometry-aware collision exclusion), and incorrect fan-node counts for acute angles (resolved by implementing adaptive arc-length-based fan sizing). These corrections required domain-specific knowledge that the AI could not independently provide.

Case B: Complete GUI framework. The PyQt6 application comprises 69 Python source files totaling over 18,000 lines, organized in an MVC architecture with 9 controller mixins, 8 data models, 16 view components, and 15 panel widgets. The AI was highly effective at generating GUI scaffolding — widget layouts, stylesheet definitions, signal/slot wiring — which constitutes the majority of GUI code by volume. The expert focused on specifying the interaction logic, mode-switching behavior, and ensuring consistent dark-theme aesthetics across all panels.

Case C: Solver pipeline integration. This was the most complex integration task, requiring the worker to: feed interactive stdin to the getPGrid converter, manage case directory structures with file renaming and path rewriting, parse real-time solver stdout for convergence monitoring, and handle both IBM (Immersed Boundary Method) and non-IBM solver output formats — which were discovered during live testing to have different stdout structures. The initial implementation plan (solver_integration_plan.md) was written collaboratively with the AI, documenting 8 key design decisions and 9 risk items, then executed phase-by-phase.

The phased implementation plan estimated a total effort of approximately 20–25 person-hours for the solver integration module alone (10 phases, see [4]). Based on the authors' experience, developing the equivalent GUI application through conventional methods (manual coding without AI assistance) would typically require 3–6 months for a team of comparable domain expertise but limited software engineering background. The AI-assisted approach compressed this to approximately 4–6 weeks of part-time effort.

We observed that the AI was most effective for: (i) GUI boilerplate and layout code, (ii) file I/O and data parsing routines, and (iii) standard software patterns (MVC wiring, command pattern, worker threads). Conversely, the AI required the most correction for: (i) domain-specific edge cases in numerical algorithms, (ii) interaction with third-party SDKs with limited training data (e.g., Gmsh API), and (iii) cross-component integration where multiple subsystems must agree on file formats and directory conventions.

The workflow proceeded as follows: (1) the NACA 0012 profile was loaded and resampled using cosine spacing for leading- and trailing-edge refinement; (2) HybMesh2D generated a hybrid mesh with 20 boundary layers (initial thickness 0.0002, growth rate 1.1), producing approximately 100,000 elements; (3) the solver mode invoked getPGrid for format conversion, then launched UNICONES with pthread parallelism; (4) convergence residuals were monitored in real time via the GUI; and (5) the resulting Mach number field was visualized with smooth contours and velocity streamlines, all without leaving the application.

The full-chain test confirmed format compatibility at every interface: HybMesh2D's STAR-CD output was correctly consumed by getPGrid, the resulting grid files were properly ingested by UNICONES, and the solver's Tecplot output was successfully parsed and rendered by the results module. The solver processed 50,426 nodes and 99,994 elements in the test case, with convergence residuals extracted every 10 iterations for the 5 conservation-variable L2 error norms.

5. Discussion

The vibe coding approach proved highly effective for developing the peripheral tooling around an existing solver — GUI interfaces, data pipelines, and visualization — while the solver core (UNICONES) remained untouched. This division aligns naturally with the strengths and weaknesses of current LLMs: they excel at well-established software patterns (GUI frameworks, file I/O, standard algorithms) but struggle with domain-specific numerical logic and poorly documented APIs.

A critical enabler was the domain expert's ability to validate the generated output against physical expectations. Without this capability, vibe coding for scientific software carries significant risks of producing plausible but incorrect implementations. We therefore emphasize that our approach is not "pure" vibe coding (fire-and-forget AI generation) but rather a responsible AI-assisted engineering model where the human retains full accountability for correctness.

Unlike commercial pre/post-processing tools (e.g., Pointwise, ANSYS ICEM), HybMesh2D is intentionally lightweight and tightly coupled to a specific solver. This focused scope is precisely what makes the vibe coding approach viable: the development target is well-defined, the acceptance criteria are clear (the solver must run and produce correct results), and the user base (researchers and students using UNICONES) has known needs. We suggest that this pattern — AI-assisted construction of solver-specific front-ends — is broadly reproducible across the computational science community.

6. Conclusion

We presented HybMesh2D, an integrated pre/post-processing platform for the UNICONES CFD solver, developed using an AI-assisted vibe coding approach. The platform unifies geometry preparation, hybrid mesh generation, solver execution with real-time monitoring, and flow-field visualization into a single graphical application. The AI-assisted methodology enabled domain experts — who are not professional software engineers — to produce a production-quality platform of over 21,000 lines of code in a fraction of the time that conventional development would require.

This work demonstrates the viability of vibe coding for scientific software tooling, provided that the domain expert retains control over algorithm design and output validation. Future work includes extending the platform to support 3D mesh generation, adding automated parameter optimization, and exploring web-based deployment to further lower the barrier to entry for CFD education and research.

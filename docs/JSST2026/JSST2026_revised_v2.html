Abstract

This paper presents an integrated pre- and post-processing platform for CFD solvers, developed using an AI-assisted paradigm known as responsible vibe coding. Motivated by the accessibility gap between mature in-house CFD solvers and their practical adoption in academic settings, we built a unified graphical application spanning geometry preparation, hybrid mesh generation — combining structured boundary-layer quadrilaterals with unstructured far-field triangles — solver execution with real-time convergence monitoring, and flow-field visualization. The platform was demonstrated with the UNICONES compressible flow solver [1] and constructed using Claude Code and the Antigravity CLI in agentic mode, in which the domain expert retains full responsibility for architectural decisions and physical validation while the AI accelerates implementation. This collaboration produced over 21,000 lines of code in approximately 4–6 weeks of part-time effort. The methodology suggests a generalizable pattern for research groups seeking to lower the adoption barrier of in-house solvers without dedicated software engineering resources.

Keywords: CFD pre/post-processing; CESE method; hybrid mesh generation; vibe coding; AI-assisted software development; solver front-end

1. Introduction

Computational Fluid Dynamics (CFD) has become an indispensable tool in aerospace, mechanical, and environmental engineering. However, the practical use of a CFD solver is seldom limited to the solver itself — a complete simulation workflow typically involves (1) geometry preparation and surface discretization, (2) volume mesh generation with boundary-layer resolution, (3) solver configuration and execution, and (4) post-processing and visualization of results. Each of these steps often requires separate software tools, manual file conversions, and substantial expertise in both numerical methods and software operation.

This challenge is particularly acute for research groups that develop and maintain in-house solvers. UNICONES [1], a compressible Euler/Navier–Stokes solver based on the Conservation Element and Solution Element (CESE) method, developed at the National Center for High-performance Computing (NCHC), Taiwan, is one such example. The solver is intended for broader academic use and is available to interested researchers upon inquiry. In practice, however, the full simulation workflow requires coordinating multiple preprocessing utilities, manual file format conversions, and solver configuration steps that are not yet documented in a user-facing interface. As a result, familiarization typically demands several weeks of guided effort, and hands-on experience has so far remained limited to a small number of interns and collaborators. This gap — between a mature, validated solver with open-access intent and the operational complexity that impedes its adoption — is representative of a broader problem faced by the computational science community.

To address this, we developed an integrated graphical platform that unifies the complete CFD simulation pipeline — geometry preparation, hybrid mesh generation, solver execution, and flow-field visualization — into a single application, eliminating the manual file conversions and configuration steps that impede adoption. The platform is demonstrated with UNICONES, but its modular architecture is designed with extensibility to other solvers in mind. A distinctive feature of this work is the development methodology: the platform was built through responsible vibe coding [2], an AI-assisted programming paradigm in which a domain expert describes requirements in natural language and collaborates with a large language model (LLM) to produce working software. This approach enabled a team without dedicated software engineering resources to deliver a production-quality platform of over 21,000 lines of code in a fraction of conventional development time — demonstrating that solver-specific front-ends need not require a separate software engineering team to realize.

This paper makes the following contributions: (i) the design and implementation of an integrated pre/post-processing platform that lowers the barrier to adoption of in-house CFD solvers for academic users; (ii) a documented case study of vibe coding applied to scientific software development, with quantitative observations on development efficiency and human–AI role division; and (iii) a generalizable pattern for constructing solver-specific GUI front-ends via AI-assisted development, applicable to research groups maintaining in-house solvers across the computational science community.

2.1 PreProcessor Module

The PreProcessor provides an interactive geometry canvas for loading, viewing, and resampling surface discretizations. It supports multiple point-spacing strategies including uniform, cosine, geometric, and hyperbolic tangent distributions, enabling independent control over leading- and trailing-edge clustering. Automatic sharp-corner detection identifies feature points where the turning angle exceeds a configurable threshold, allowing the geometry to be split into segments with separate resampling parameters. The resampling backend is implemented as a standalone C++ executable, communicating with the GUI via a QThread worker to maintain interface responsiveness.

2.2 Hybrid Mesh Generator

The mesh generation core (C++, ~1,500 lines) produces 2D hybrid meshes comprising structured quadrilateral boundary layers and unstructured triangular far-field elements. Boundary layers are grown outward from the surface using a node-marching algorithm, with dedicated handling for convex and concave corners. A configurable transition region bridges the boundary-layer zone to the far-field, where the Gmsh library [3] generates unstructured triangles via the Frontal-Delaunay algorithm. The module exports both VTK format for standalone visualization and STAR-CD format (.vrt/.cel/.bnd) for solver input.

2.3 Solver Integration

The solver integration module orchestrates the full execution chain from within the GUI: mesh format conversion, optional domain decomposition for MPI parallelism, and solver execution in pthread parallel mode. The module automatically constructs the required case directory structure and generates the solver input configuration. During execution, a background worker parses solver output in real time, extracting iteration counts, CFL numbers, and L2 residuals for five conservation variables, displayed on a live convergence monitor. Although the current implementation targets UNICONES, the solver integration layer is designed as a modular component; adaptation to alternative solvers requires only replacement of the format conversion and stdout-parsing routines.

2.4 Results Visualization

The results module parses Tecplot-format output files and renders cell-centered scalar fields using an embedded matplotlib canvas. It supports smooth contour rendering, velocity streamlines, and vector glyphs. Users can interactively select field variables, adjust colormaps and color scale limits, and toggle mesh wireframe overlays — all without leaving the application.

3. AI-Assisted Development Methodology

The platform was developed using an approach we characterize as responsible vibe coding — a mode of AI-assisted programming where a domain expert maintains full architectural control and validation responsibility, while delegating implementation to an LLM-based coding assistant. This section describes the workflow, provides concrete examples, and evaluates the development efficiency.

3.1 The Human–AI Collaboration Model

Vibe coding, as originally described by Karpathy [2], refers to a programming paradigm in which the developer describes intent in natural language and an AI generates the corresponding code. In our context, we adopt a more disciplined variant — responsible vibe coding — in which the domain expert maintains full architectural control and validation responsibility. The primary tools used were Claude Code and the Antigravity CLI, both operating in an agentic mode: rather than simple chat-based code generation, the AI could directly read and write project files, execute the codebase, and inspect runtime outputs. This capability proved critical for diagnosing issues that could not be resolved through textual description alone (see Section 3.2, Case A).

The domain expert was responsible for defining the simulation pipeline architecture and data flow, specifying numerical algorithms, designing the format compatibility chain between pipeline components, and validating all outputs against known physical solutions. The AI was responsible for generating GUI boilerplate, implementing file parsers, producing C++ routines from algorithmic descriptions, and wiring the controller–worker–view architecture. Development proceeded iteratively — describe, generate, execute, validate, correct — typically converging within 2–5 rounds per feature.

3.2 Representative Development Cases

Case A: Boundary-layer generation. The expert described the outward-marching algorithm — including normal vector computation, fan-element geometry at convex corners, and the concave-node blending strategy — in natural language, and the AI produced an initial 610-line C++ implementation. This case illustrated three distinct challenges in human–AI collaboration. First, the quality of the AI's output was strongly dependent on the precision of the human's problem description: more carefully worded prompts consistently reduced the number of correction rounds. Second, textual description alone was often insufficient; the AI required access to actual run results to correctly diagnose geometric edge cases, such as self-intersection at sharp trailing edges and incorrect fan-node counts for acute angles. Third, even after the AI confirmed that a fix was correct, discrepancies emerged during real use — highlighting that AI self-verification carries blind spots that only domain-expert validation can catch. These three layers of human oversight — precise description, execution-based diagnosis, and physical validation — proved essential throughout the development process.

Case B: Complete GUI framework. The PyQt6 application comprises 69 Python source files totaling over 18,000 lines, organized in an MVC architecture with 9 controller mixins, 8 data models, 16 view components, and 15 panel widgets. The AI was highly effective at generating GUI scaffolding — widget layouts, stylesheet definitions, signal/slot wiring — which constitutes the majority of GUI code by volume. Human judgment remained essential, however, for decisions that required understanding of the overall user workflow: specifying mode-switching behavior, ensuring interaction consistency across panels, and maintaining a coherent dark-theme aesthetic throughout the application. These are concerns that the AI could implement once specified, but could not independently define.

Case C: Solver pipeline integration. This was the most complex integration task, requiring the worker to manage case directory structures with file renaming and path rewriting, parse real-time solver stdout for convergence monitoring, and handle both IBM (Immersed Boundary Method) and non-IBM solver output formats — which were discovered during live testing to have different stdout structures. The initial implementation plan was written collaboratively with the AI, documenting 8 key design decisions and 9 risk items, then executed phase-by-phase.

4. Discussion

The vibe coding approach proved most effective for developing the peripheral tooling around an existing solver — GUI interfaces, data pipelines, and visualization — while the solver core (UNICONES) remained untouched. This division aligns naturally with the capabilities of current LLMs: they excel at well-established software patterns such as GUI frameworks, file I/O, and standard algorithms, but require substantial human guidance for domain-specific numerical logic. Critically, as demonstrated in Section 3.2, effective collaboration depends not only on the AI's code generation ability, but on three layers of human oversight: the precision of problem description, execution-based diagnosis of edge cases, and physical validation of results. Without domain expertise at each of these layers, vibe coding for scientific software carries significant risk of producing plausible but incorrect implementations.

The modular design of the solver integration layer (Section 2.3) is a deliberate architectural choice with extensibility in mind. Adapting the platform to a different solver requires replacing two components: the mesh format conversion routine and the stdout parser for convergence monitoring. The remaining modules — geometry preprocessing, mesh generation, and visualization — operate independently of the solver and require no modification. This separation of concerns suggests that the platform architecture could serve as a reusable template for other research groups seeking to build front-ends for their own in-house solvers, with relatively limited additional effort.

Unlike commercial pre/post-processing tools such as Pointwise or ANSYS ICEM, the present platform is intentionally lightweight and tightly coupled to a specific simulation context. This focused scope is precisely what makes the vibe coding approach viable: the development target is well-defined, the acceptance criteria are clear, and the user base has known needs. We suggest that this pattern — AI-assisted construction of solver-specific front-ends by domain experts without dedicated software engineering resources — is broadly reproducible across the computational science community. The platform is available to interested researchers upon inquiry.

5. Conclusion

We presented an integrated pre/post-processing platform for CFD solvers, developed using an AI-assisted responsible vibe coding approach and demonstrated with the UNICONES compressible flow solver. The platform unifies geometry preparation, hybrid mesh generation, solver execution with real-time monitoring, and flow-field visualization into a single graphical application. The AI-assisted methodology enabled domain experts — without dedicated software engineering resources — to produce a platform of over 21,000 lines of code in approximately 4–6 weeks of part-time effort, a fraction of conventional development time.

The modular solver integration architecture suggests a path toward a more general CFD front-end framework, where the geometry, mesh, and visualization components are reused across different solvers. Promising directions for future work include extending the platform to 3D mesh generation, incorporating automated parameter optimization for mesh quality, and exploring web-based deployment to further lower the barrier to entry for CFD education and research.

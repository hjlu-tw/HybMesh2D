# Block topology for multi-element airfoils in 2D

**A RESEARCH NOTE.** Not `.claude/rules/*.md` (what the rule is), not `docs/design_notes/`
(why a shipped rule was chosen). It records what the workshop guidelines, the NASA pages, the
vendor documentation and the published literature actually say about how 2-D multi-element
sections (main + slat and/or flap) are blocked for STRUCTURED solvers, so that a decision about
this repo's `MESH_MODE 1` path can be argued from sources rather than from taste. Nothing here
is binding; no rule, gate, test or source file was changed to write it. 2026-10-14.

**Subject.** This repo's structured path fills a DECLARED topology (corners, edges, blocks;
an edge may bind to a CAD segment by arc length; node counts PROPAGATE across shared edges).
A two-element case was built as two 8-block O-rings, each wrapped to an AXIS-ALIGNED
RECTANGULAR box embedded in a Cartesian H grid: 0 inverted cells, but a neighbouring-cell area
ratio reaching 23×. Anchoring one element C-grid-style (trailing edge tied to the box's
downstream boundary node, so the wake radial is straight) improved mean non-orthogonality by
14% but folded cells unless a grid line passed exactly through that trailing edge. The
question this note answers is whether the field builds per-element rings against rectangular
outer boundaries at all, and how two elements' regions are allowed to interlock.

## How to read the markers

- **[V]** verified in a primary source I read myself (the document's own text, a NASA page, a
  vendor manual, a paper's body).
- **[I]** my own inference or derivation from a **[V]** fact. Stated as reasoning, not fact.
- **[2nd]** I could only find this secondhand. Treat as unconfirmed.

## Lead: the four answers that decide the question

### L1 — No. Nobody in anything I read wraps an element's ring to a rectangle and makes it CONFORM to a surrounding Cartesian H grid. **[V] on what they do; [I] on the absence.**

The two published 2-D structured grid systems for the canonical three-element section
(30P30N) both do the same thing, nineteen years apart, and neither is a conforming
rectangle-in-H-grid:

- **Liou & Liu, AIAA 99-3177** (grids by NASA's `OVERMAGG`): "The computational grid consists
  of seven zones and a total of about 103,000 grid points … the C grids around the slat, the
  main element, and the flap, which consist of 175×45, 381×133, and 221×85 points,
  respectively. **Two H grids were used for the main-element cove and for the wake region of
  the flap.** A background H grid extends to the top and the bottom walls of the wind tunnel.
  When the grid for one element overlaps another element(s), **holes and outer boundaries are
  determined by using the PEGSUS code**." **[V]**
- **Housman, Stich & Kiris, BANC-V (NTRS 20190030756)**, grids by Chimera Grid Tools v2.1p:
  "A consistent family of two-dimensional structured overset grid systems … consisting of **5
  grid zones: the slat, main element, flap, slat cove, and an off-body grid** … The grid
  generation process consists of **hyperbolically marching from an initial discretized
  center-span curve** representation of the geometry using a specified wall spacing. **O-grids
  are used for the main-element and flap**, but the slat grid has a highly-concave cove region,
  so the **boundaries of the grid in the cove were allowed to splay over each other** as well
  as the solid surface of the slat. In the slat cove region, **a specially designed H-grid**
  is generated by hyperbolically marching in both directions from an initial curve which starts
  at the slat leading edge, continues through the slat cove to intersect tangentially with the
  slat trailing edge and downstream over the main element until roughly 0.2 chord … the
  off-body grid was generated as a **simple stretched Cartesian grid** with fine uniform
  spacing in the region of interest." **[V]**

In both, each element's near-body mesh has a **body-following outer boundary that is a RESULT
of marching, not an input** — and the elements interlock by **overlap and hole-cutting**, not
by shared edges. The Cartesian grid is there; the conformity is not.

### L2 — The rectangle is not a strange idea, though: it is what the mainstream structured GUI does, and the vendor documents say so. **[V]**

ANSYS ICEM CFD's own manual: "The O-grid creation capability is simply **the modification of a
single block or blocks to a 5 sub-block topology** … the O-grid shown below is created
**entirely inside the selected block**. … When the O-grid is generated, **the size of the O-grid
is scaled based upon the Factor** in the Blocking > O-grid parameter window." Block edges
interior to the volume are "Blue Edges … These edges are in the volume", i.e. free, projected
to nothing (*ANSYS ICEM CFD/AI\*Environment 10.0 User Manual*, §3.8, §3.10.1, §3.7). **[V]**

So in the dominant interactive route, an element's O-ring outer boundary is **an inset copy of
whatever block you selected**. Select a rectangle, get a rectangle. That is exactly the
construction this repo built, and it is not an eccentric one — but it is a consequence of the
tool's block algebra, not a recommendation anyone wrote down, and I found no paper or manual
that argues FOR a rectangular ring boundary. See "Gaps".

### L3 — The reason the field left point-matched multi-block for this geometry class is published, in one sentence, with a number beside it. **[V]**

GMGW-1's own summary (Chawner et al., NTRS 20180006182), assessing the HL-CRM meshes: "all
three [structured grids] failed the skew test with roughly 40% of cells having skew values
less than 0.8. … the committee's overset grid meeting the criterion except for approximately
1% of the points … **The committee's multi-block structured grid exhibited more
non-smoothness with approximately 5% of points exceeding the criterion. This might be
explained by the point matching topology requirements of a multi-block versus an overset grid
which cause the grid lines to take more circuitous paths.**" **[V]**

And the block counts for the *same geometry* say it louder than the prose. From the workshops'
own grid READMEs on `hiliftpw-ftp.larc.nasa.gov`: **[V]**

| geometry | point-matched structured | structured overset |
|---|---|---|
| HiLiftPW-1 Trap Wing (3 elements) | `Str-OnetoOne-A`, Boeing Huntington Beach: **1235 zones** | `Str-Overset-A`, Boeing Huntington Beach: **34 zones** |
| HiLiftPW-3 HL-CRM, full flap gap | `C-HLCRM_Str1to1_GridPro`: **1930 zones** (2086 for the partially-sealed gap) | `A-HLCRM_StrOverset_ChimeraGridTools` V4: **72 blocks** (C/M), 76 (F), 102 (XF) |

A factor of **36** and a factor of **27** in block count, on the same two geometries. These are
3-D, so the ratio is not transferable to 2-D as a number — but the mechanism (the point-matched
grid must propagate every split everywhere) is dimension-independent. **[I]**

The migration itself is visible in the committee inventories rather than stated as policy
anywhere I found: **[V]**

- **HiLiftPW-1 (2010)**: of the ten committee grid series, **two were structured point-matched**
  (`Str-OnetoOne-A`, `-B`), one structured overset (`Str-Overset-A`), seven unstructured — and
  two of those seven are the point-matched grids translated to unstructured hexahedra
  (`Unst-Hex-FromOnetoOne-A`/`-B`). Participants supplied two further point-matched series
  (`Str-OnetoOne-D`, `-E`) and one Cartesian/Lattice-Boltzmann set. (Rumsey, Long, Stuever &
  Wayman, NTRS 20110002879, Table 2, cross-checked against
  `hiliftpw-ftp.larc.nasa.gov/HiLiftPW1/OriginalGrids/`.)
- **HiLiftPW-3 (2017)**: five committee families — **one** point-matched (GridPro), one overset
  (CGT), three unstructured (Pointwise). Of the **18 participant-generated families**, exactly
  one is structured, and it is overset (`g-HLCRM_StrOverset_PW`).
- **HLPW-4/GMGW-3 (2022)**: the committee RANS mesh families are 1.1 Tet, 1.2 Prism-Tet, 1.3
  Hex-Tet, 2.1 Tet, 2.2 Prism-Tet, 2.3 Hex-Tet, 5.3 Hex-Tet, **3 (Overset)** and **4
  (Overset)** — **no point-matched structured family at all** (NTRS 20220005271, Fig. 2).

The 2-D case is the same picture. NASA's Turbulence Modeling Resource case **VERIF/2DMEA**
(the only multi-element case on the TMR — see "Gaps") states its own purpose as "to provide a
large sequence of **unstructured** grids of ostensibly the same family", and offers four grid
sets: two unstructured families, **one structured OVERSET family** (added 2021-02-25, "custom
tailored (by hand) to yield wake clustering", ~46,000 to 3.2 million points per plane, and
"CFD results on these grids are currently not provided on this website"), and MIT's adapted
meshes. **There is no conforming structured multi-block grid for the 2-D case.** **[V]**

### L4 — But conforming multi-block in 2-D is not dead, and the one paper that gives a number gives 26 blocks for three elements. **[V]**

Kim, Alonso & Jameson, *Design Optimization of Multi-Element High-Lift Configurations Using a
Viscous Continuous Adjoint Method* (Stanford; 30P30N): "The high-lift configuration parallel
design method uses a **point-to-point matched multi-block grid system** … Multi-block viscous
and inviscid meshes were generated using either a **C- (viscous) or O-topology (inviscid)** …
**One-to-one point connectivity between block faces is employed** to ensure conservation across
boundaries … **The C-topology mesh has 26 blocks of varying sizes and a total of 204,800
cells.**" **[V]** (The conclusion of the same paper says "26 blocks and a total of 204,800 mesh
**points**" — an internal inconsistency in the paper, noted rather than resolved.)

Two further conforming-ish 2-D data points, both weaker and both marked as such:

- **Chen et al., ICCFD7-2012-2402** (Tsinghua / COMAC), the **Window-Embedment** strategy: "**A
  C-grid is first generated about the baseline airfoil. Then two windows are opened for the
  slat and flap respectively. Two H-grids are generated for them, as well as the cutted
  geometry of the main element, in the windows.**" The interfaces are **patched (non-matching)**
  — their solver's companion paper is Zhang, Chen & Fu, "Improvement to Patched Grid Technique
  with High-Order Conservative Remapping Method", *J. Aircraft* 48(3) 884–893 (2011). **[V]** on
  the quoted topology; **[2nd]** on the remapping scheme, whose body I did not read.
- A 2024 *Physics of Fluids* machine-learning paper (36, 103608, doi 10.1063/5.0228104) reports
  a real block-structured 30P30N grid: "The numbers of grid points, blocks, and interfaces are
  **48 764, 33, and 66** … The complexity of this geometry entails **more curved interfaces and
  damages the orthogonality of the structured grid**." **[V]** that the grid exists with those
  counts; it is a **Re = 1000** demonstration grid in a rectangular box, not a RANS high-lift
  grid, so the counts are a lower bound on what a viscous grid would need. **[I]**

## 1. Named topology families, and which is standard

**[V]** Four named families appear, and the workshops' own participant tables name all of them
in one sentence. Choudhari & Lockard's BANC-III Category 7 (30P30N) assessment, NTRS
20160006011, lists the meshing techniques used: "structured grid with **contiguous, patched, or
overset interfaces between adjacent blocks**, Cartesian meshes coupled with **immersed boundary**
techniques or surface elements, and **unstructured** grids."

**C-grid per element.** Liou & Liu's 30P30N (above): a C-grid round slat, main and flap.
Kim/Alonso/Jameson's conforming mesh: C-topology for the viscous case, O-topology for the
inviscid one. Chan et al.'s rule for *why*: "Typically a **C-grid is chosen for wings to
provide grid resolution in the wake region and to avoid wrapping a grid around the obtuse
angle of a sharp trailing edge**." (*Best Practices in Overset Grid Generation*, AIAA 2002-3191,
§4.1.3.) **[V]**

**O-grid per element.** The same section gives the counter-rule: "Conversely, configurations
where the wing wake does not impinge on other aerodynamic surfaces, or for geometries with
thick trailing edges …, **the wake may be more conveniently resolved with an O-grid**. Even for
a relatively sharp NACA 0015 airfoil, Fig. 21 shows a **difference of only about 5% between
O-grid and C-grid drag polars**." **[V]** The modern NASA 2-D 30P30N system (LAVA/CGT) picks
O-grids for main and flap anyway — *in a case where the main's wake certainly does impinge on
the flap* — because the overset machinery resolves the wake in the off-body Cartesian grid and
in the flap's own mesh, not along a wake cut. **[I]** on the attribution of the choice; **[V]**
that O-grids are what they used.

**H-grid patching.** H blocks appear in every system I read, but as the **filler**, never as
the element's own ring: the slat cove H-grid and the flap-wake H-grid in Liou & Liu, the slat
cove H-grid in LAVA, the background H grid to the tunnel walls in Liou & Liu, the stretched
Cartesian off-body grid in LAVA, and the two embedded H-grid windows in Window-Embedment.

**Overset / chimera as the alternative.** The comparison is as old as the subject: Rogers,
Wiltberger & Kwak, AIAA 92-0405, "Efficient simulation of incompressible viscous flow over
single and multi-element airfoils", compared "**a patched system of grids and an overlaid
Chimera system of grids**" on two-, three- and four-element configurations. **[V]** (abstract
only — see "Gaps"). Overset won in practice; the evidence for that is L3's inventories, not a
sentence in that paper.

**The honest summary.** For a 2-D multi-element section solved with a structured code, **the
standard today is structured overset: one body-fitted mesh per element plus one or more
cove/gap meshes, floating in a Cartesian off-body grid.** The reasons given are (a) the
circuitous grid lines that point-matching forces (GMGW-1, L3), (b) that each near-body mesh
needs only its own surface as input — "hyperbolic volume grid generation only requires the
specification of a surface grid **while the remaining boundaries do not have to be
prescribed**" (Chan et al. 2002, §4.1) — and (c) that "the boundaries of such domains can be
placed **arbitrarily** provided they allow sufficient overlap between neighboring grids"
(*ibid.*, §3.2). **[V]**

Unstructured is a separate and larger migration: HLPW-4 drew 184 entries from 44 groups
against HLPW-1's 39 from 21, and almost all of the growth is unstructured and adaptive. **[V]**

## 2. The slot: the gap gets its OWN grid, and the grading rule is a constant-spacing band

**The gap region is its own zone, in every 2-D system I found.** Liou & Liu put an H grid in
the **main-element cove** (the flap well) and another in the **flap wake**; LAVA puts a
purpose-built H-grid in the **slat cove**, marched in both directions from a curve that runs
from the slat leading edge, through the cove, tangentially past the slat trailing edge and
**downstream over the main element to roughly 0.2 chord**. **[V]** It is neither "part of the
main's wake region" nor "part of the flap's C" — it is a third thing, and in both systems it
is built by marching from a hand-chosen curve rather than by subdividing a neighbour.

**The grading rule is written down, and it is not a stretching ratio — it is a band of
CONSTANT spacing whose length is set by the gap.** From the 1st and 2nd AIAA CFD High Lift
Prediction Workshop gridding guidelines, verbatim: **[V]**

> e) Recommend variable off-body cell growth rates for wing and flap grids
> 1) Growth rate in the viscous layer (GR1) should be < 1.25 for all grids
> 2) **To capture the wake from upstream elements, the wing and flap grids should include a
>    region where the growth rate (GR2) is 1.0**
> 3) **The length of the region with constant spacing should be roughly 2X the size of the
>    slat/flap gap** at the wing root … slat/flap gap = 0.015 or ~0.8" at the root

HiLiftPW-3's guidelines restate it as a direction rather than a length: "the grids should be
well-resolved across the wake regions (especially behind the slat element and behind the main
element). Use **finely spaced flow-aligned cells, where flow-aligned means that the cell's
finest spacing is in the direction of the steepest velocity gradient** (approximately normal to
the local flow direction). **Wake clustering should optimally extend well downstream, at least
over the entire distance of the wing local chord**, generally following the approximate wake
trajectory." Its figure is captioned "Example of a recommended grid profile to capture the
boundary layer and wake flow (**shown here for a structured overset mesh**)." **[V]**

HLPW-4 pushes the extent further: "Wake clustering and refinement should be enforced over the
full chord-length of both the wing and flap elements as well as **a minimum of 2 wing
chord-lengths downstream from the flap trailing edge**." **[V]**

**And the failure mode when you get the slot wrong is documented with a mechanism.** Chan et
al. 2002 §4.1.4, on Rogers' three-element airfoil: "The hole in the downstream-element grid
caused by the upstream element is in an area where the normal spacing is **too coarse**. The
grid points denoted with circles are the only fringe points which will receive data
interpolated from the wake of the upstream element. They surround the wake, but **there are no
points within the wake**. This causes the downstream grid to **entirely miss the wake velocity
defect**, and hence compute too much mass flow in this region. This mass-flow error is passed
back into the upstream-element grid … resulting in large errors in the computed pressure."
**[V]**

**For a CONFORMING grid, the one 2-D source that states a rule states a different one: match
the two facing surfaces' node distributions.** MSES — Drela's multi-element design/analysis
system, whose grid is an intrinsic streamline grid — does this automatically: "Once a good node
distribution on each element is obtained, MSET proceeds to **modify all the spacings to resolve
any conflicts between adjacent elements**. Basically, **all the distributions are automatically
fudged to make spacings on element surfaces facing each other match as closely as possible.
This prevents massive grid shearing which would otherwise occur. No such action is necessary
for single-element airfoils.**" (*MSES user guide*, §2.2.2.) **[V]** MSES also exposes the slot
resolution as a single named parameter: `M 7 Maximum streamlines between two elements`, beside
`T 19 Number of streamlines in top of domain` and `B 15 … bottom` (§2.2.5). **[V]**

## 3. Where the block corners go, the outer boundary's shape, and the wake cut

### 3a. The ring's outer boundary is a body-following curve, and in the overset practice it is not even an input. **[V]**

Chan et al. 2002, §4.1: near-body volume grids are grown by hyperbolic marching; "**With the
surface grids already designed to provide sufficient overlap, this property is inherited by the
near-body volume grids** in the vicinity of the body. **The overlap can be maintained away from
the body by applying a splay boundary condition on the floating boundaries of the volume grid**
during hyperbolic marching." And §3.8/§4: "Typically the same wall spacing, **marching
distance** and total number of points are used for all near-body grids in the marching (normal)
direction."

The 2026 state of the art automates the splay rather than removing it — Chan, Chuen, Jensen &
Schauerhamer, AIAA 2026-4121 (EPOGS): "**All near-body volume meshes in the auto-meshing scheme
are grown hyperbolically in the normal direction to the surface independently of each other.**
For J and K index boundaries that do not lie along a symmetry plane, a **splay boundary
condition** is applied in the hyperbolic marching scheme. … **Proper overlap means neighboring
meshes have 2×N_f cells overlap** in order to avoid orphan points where N_f is the number of
fringe point layers." **[V]**

So: in the practice that dominates structured high-lift, **an element's ring outer boundary is
an offset-like marched curve that bends OUTWARD at its free ends on purpose**. A rectangle
would defeat the one property the splay exists to produce.

**There is no "collar" for a 2-D element.** Chan's collar and cap grids are for **junctions and
intersections between 3-D components** — "a collar grid is then used to fill the
fuselage/wing junction", "**Flap end cap grid**" — and have no 2-D analogue. The word does not
apply to the thing the brief called a "collar shell". **[V]**

### 3b. The wake cut does not have to be straight, and the published instruction is the opposite. **[V]**

Kim, Alonso & Jameson, on the conforming 30P30N mesh: "**Grid lines are also bunched along the
expected wake trajectories of each of the elements.**" HiLiftPW-3: wake clustering "generally
**following the approximate wake trajectory**". MSES builds its block skeleton out of actual
streamlines: "a panel solution … is then used to trace **a pair of stagnation streamlines just
above and below each element**, as well as the upper and lower farfield streamlines.
**Iso-potentials emanating from all leading and trailing edges are also located. This divides
up the domain into blocks**, which are then automatically displayed … **These blocks form the
skeleton on which the grid is generated.**" **[V]** A straight wake cut appears nowhere as a
requirement in anything I read.

What *is* documented about C-grid wake cuts is two different hazards, neither of which is
straightness:

- **Viscous clustering at the cut.** "It has been found that **maintaining a y+ = 1 spacing in
  the wake can result in convergence difficulties for some flow solvers** (e.g., OVERFLOW).
  This cell spacing is unnecessarily small in the wake region, and generally does not coincide
  with the actual wake. Furthermore, one typically stretches the streamwise spacing aft of the
  trailing edge, **resulting in grid cells with extremely large aspect ratios**. One way to
  resolve these problems is to **smooth the grid in the wake region, relaxing the viscous
  clustering**" — CGT's `smogrd` tool exists for exactly this (Chan et al. 2002, §4.1.3). **[V]**
- **The "tab" at the root of the cut.** For a one-viscous-direction C topology, "the flow near
  the surface may effectively see a **partial grid-cell 'tab' at the root of the wake cut**. At
  significant angles-of-attack this can interrupt the smooth flow along the fuselage, degrading
  the accuracy of the calculation. **This can be avoided by using an H-grid topology** …
  (CH-type topology, two viscous directions)" (*ibid.*, §4.1.2). **[V]**

### 3c. The trailing edge itself has a published thickness threshold, and it is 0.2% chord. **[V]**

Chan et al. 2002, §3.2.2: "For cases where wake resolution is not critical, **an O-grid can be
used to wrap around the trailing edge.** Otherwise, a C-grid topology can be utilized in one of
several ways, depending on the trailing edge thickness compared to the streamwise grid spacing
at the trailing edge. **If the thickness is less than 0.2% of the local chord, it is recommended
that the grid be continued aft of the trailing edge and the gap closed in the first point in
the wake.** If the trailing edge thickness is greater than 0.2% chord, this approach can result
in **too abrupt a change in grid spacing and direction**. An alternative is to wrap the surface
grid onto the base and then out the wake. **The drawback to this second approach is that it
tends to result in unsmooth, skewed grids.**"

That is the closest thing in the literature to this repo's observed fold: a C anchoring whose
trailing-edge spacing and direction do not line up produces an abrupt change, and the published
remedies are either (a) collapse the first wake point (a deliberate degenerate cell) when the
base is thin enough, or (b) accept skew, or (c) do not use a C at all. **[I]** on the
connection to this repo's measurement; **[V]** on the quotation.

### 3d. How the main's wake cut is terminated when the flap sits in its wake: in every system I found, it isn't. **[V]**

- **LAVA/CGT 30P30N**: the main element has **no wake cut** — it is an O-grid. The wake is
  carried by the off-body Cartesian grid and interpolated into the flap's O-grid.
- **Liou & Liu 30P30N**: the main element's C-grid wake simply **runs on and is overlapped**;
  "holes and outer boundaries are determined by using the PEGSUS code". The flap has its own
  C-grid and its own wake H-grid.
- **Window-Embedment**: the main element's C-grid is the grid of the **stowed/baseline**
  airfoil; the flap lives in a window cut into it, so the question of terminating the main's
  wake cut on the flap never arises.
- **MSES**: the main element's wake IS a stagnation streamline of the solution; it passes over
  the flap by construction and can never intersect it.

I found **no** source describing a conforming structured grid in which the main element's wake
cut is terminated on the flap's block boundary. That is not proof that nobody does it — see
"Gaps" — but it is the shape of the absence.

## 4. Element-to-element interface: all three exist, and the workshops require none of them

**The gridding guidelines do not rule on this at all, and that is worth stating plainly.** I
read all four HiLiftPW / HLPW mesh-generation guideline documents end to end
(HiLiftPW-1 11JUN09, HiLiftPW-2 v2 March 2013, HiLiftPW-3 v10 June 2016, GMGW-3/HLPW-4
Mesh Generation Guidelines v11.3). **None of them mentions block topology, block counts,
point-matched versus patched versus overset interfaces, or how two elements' meshes should
meet.** They are sizing documents: wall spacing, y+, growth rate, trailing-edge cell counts,
leading/trailing-edge chordwise spacing, farfield distance, wake resolution, refinement
factors, and (for structured meshes) multigrid-friendliness. The only topology-adjacent
sentences are HiLiftPW-3's figure caption "shown here for a structured overset mesh" and
HLPW-4's "**Structured Meshes** – Ensure that meshes are consistent as described above. Making
your meshes multi-grid friendly is **not a requirement**." **[V]**

So the workshops **permit** all three and **require** none. What the participants did:

- **Fully conforming (point-matched / one-to-one).** HiLiftPW-1's `Str-OnetoOne-A/B/D/E`;
  HiLiftPW-3's GridPro `C-HLCRM_Str1to1`; in 2-D, Kim/Alonso/Jameson ("One-to-one point
  connectivity between block faces is employed **to ensure conservation across boundaries** and
  to provide for continuity of the grid at block interfaces"). The stated benefit is
  **conservation**; the measured cost is GMGW-1's "circuitous paths" and the 27–36× block count.
  **[V]**
- **Non-matching / patched with interpolation.** Window-Embedment's embedded H-grid windows
  against the background C-grid, with a **high-order conservative remapping** method written
  specifically for the interface (Zhang, Chen & Fu, *J. Aircraft* 48(3) 2011). BANC-III
  submission 08 (ElaN3D, TU Berlin) is listed with "**hanging node block interfaces**". **[V]**
- **Overset.** Double fringe layers in LAVA ("**Double fringe layers are enforced throughout
  all overlap regions** to ensure proper communication between grids"); 2×N_f cells of overlap
  as the formal requirement in EPOGS; PEGSUS/PEGASUS and C3P as the connectivity codes; and the
  one hard sizing rule Chan et al. give for it: "**grid spacings from neighboring grids in the
  overlapped zones should be comparable**. A common mistake is to dump the wake of an airfoil
  C-grid into a coarse background Cartesian mesh a short distance downstream from the airfoil."
  **[V]**

## 5. Published rules of thumb

**Block counts.** For three elements in 2-D: **26 blocks** conforming C-topology (Kim, Alonso &
Jameson); **33 blocks / 66 interfaces** block-structured at Re = 1000 (*Phys. Fluids* 36,
103608); **7 zones** overset (Liou & Liu); **5 zones** overset (LAVA). In 3-D on the same
geometry: 1235 vs 34 zones (Trap Wing) and 1930 vs 72–102 (HL-CRM). **I found no published
block count for a TWO-element 2-D section** — see "Gaps". **[V]**

**Blocks around one element.** Nobody states a number as a rule. What is stated is the
*surface* point budget: "The use of **101 grid points on the upper surface and 101 points on
the lower surface** will avoid high grid stretching and maintain adequate resolution when using
these leading and trailing edge clusterings. **More points may be needed for good communication
between high lift elements**" (Chan et al. 2002, §3.4.1). The 2-D 30P30N C-grids of Liou & Liu
are 175×45 (slat), 381×133 (main), 221×85 (flap) — i.e. roughly 2× as many surface points on
the main as on either device, and the radial counts scale the same way. **[V]**

**Singular / degenerate corners — where they are tolerated.** Three documented tolerances, and
no general rule: **[V]**

- "**Three-sided domains are sometimes used near surface feature points**" (Chan et al. 2002,
  §3.2).
- The collapsed first wake point at a thin blunt trailing edge (§3c above).
- "At least **5 points should be used on any geometric feature**" — the floor below which a
  feature is not resolved at all (*ibid.*, §3.4), since most flow solvers "utilize a 3 to 5
  point differencing stencil".

**Growth rate.**

- HiLiftPW-1/-2: "Growth rate in the viscous layer (GR1) should be **< 1.25 for all grids**",
  with the constant-spacing wake band at **GR2 = 1.0**. **[V]**
- HiLiftPW-3 scales it with refinement: "GR1c ~ 1.25 for the Coarse grid, **GR1m ~ 1.16** for
  the Medium grid, **GR1f ~ 1.10** for the Fine grid, and **GR1xf ~ 1.07** for the Extra-Fine
  grid", via `(GR1)**(1/F**n)` with F ~ 1.5. HLPW-4's table repeats 1.25 / 1.16 / 1.10 / 1.07 /
  1.05 / 1.03 for levels A–F. **[V]**
- TMR VERIF/2DMEA Family 1 stretching rates, L1→L7: 1.25 / 1.17 / 1.12 / 1.08 / 1.06 / 1.04 /
  1.03. **[V]**
- Overset practice is slightly looser and two-sided: "In practice, **a stretching ratio of 1.2
  or below for surface grids and 1.3 or below for volume grids** is found to work well" (Chan
  et al. 2002, §3.4). Chan's own HL-CRM grid measured "The range of the local stretching ratio
  is about **1.05 to 1.3** … my estimate is that it is **very close to 1.2**"
  (GMGW-1 questionnaire, `GMGW-1-Questionaire-OversetStruc-WMChan.docx`). LAVA's 2-D 30P30N
  family reduces it as `1.25^(1/r)` with r = 1.0, 1.4, 2.0, 2.6. **[V]**
- Everyone asks for a constant-spacing band at the wall: "Recommend grids have **at least 2 cell
  layers of constant spacing normal to viscous walls**" (HiLiftPW-1 b, -2 d, -3 §2). Chan et al.
  measured why: on a flat plate, "even **2 cells of constant spacing removes the stretching
  dependence on the skin friction**" (§4.1.1). **[V]**

**Surface clustering.** LE spacing **0.1% of local chord**, TE spacing **0.2% chord** (Chan et
al. 2002, §3.4.1) — against the workshops' **0.1% of the LOCAL DEVICE chord** at both LE and TE,
"use the local slat-element chord for slat grid, wing-element chord for wing grid and
flap-element chord for flap grid" (HiLiftPW-2 i.1, HiLiftPW-3 §4.b). Trailing-edge base: **4 /
6 / 9 / 14 cells** across for coarse / medium / fine / extra-fine (HiLiftPW-1 i, -2 k); HLPW-4's
levels A–F use 4 / 6 / 9 / 12 / 18 / 27. **[V]**

**Farfield.** 100 C_REF in HiLiftPW-1/-2/-3; **1000 C_REF** in HLPW-4 and on the TMR 2-D case.
MSES, which uses a high-order farfield representation instead, recommends a *rectangle* of
`XINL XOUT YBOT YTOP = -1.75 2.75 -2.0 2.5` for a unit chord, and says the sensitivity to it is
low. **[V]** This is the one place a rectangle is unambiguously standard — and it is the
**global** outer boundary, not an element's ring.

## 6. What this bears on, for this repo's two-element case

Stated as inference, because none of the sources was written about this tool. **[I]**

1. **The rectangle is the likely structural cause of a large area ratio, and the geometry is
   arithmetic.** For a square box of half-width `a` centred on a body, the centre-to-corner
   distance is `a√2` and the centre-to-edge-midpoint distance is `a`. A ring filled with the
   same number of radial cells at every station therefore carries a **≥1.41× built-in variation
   in radial cell size before the body's own shape contributes anything**, and for a 2:1 box the
   ratio between the corner ray and the short-edge ray is `√1.25 / 0.5 = 2.24`. Combined with
   the circumferential mismatch between arc-uniform on the body and arc-uniform on a rectangle,
   neighbouring-cell area ratios in the tens are what the construction produces. Nothing in the
   literature fights this, because nothing in the literature uses a rectangle there.
2. **The published alternative to a declared rectangle is a declared BODY-FOLLOWING outer
   curve** — and this repo already has the machinery for one: #152's offset-derived middle ring
   (`services/geometry_offset.py`, `examples/geometries/ellipse_offset.dat`) is exactly a
   marched, body-following seam declared as a `follows` edge. The overset practice's
   outward-splayed marched boundary is the same object with its ends bent out.
3. **The C-anchoring fold has a named published remedy, and it is not "move a grid line onto
   the trailing edge".** Chan's 0.2%-chord threshold (§3c) says: below it, collapse the gap at
   the first wake point — a deliberate degenerate cell — and above it, expect skew. Neither
   option is "make the wake radial straight".
4. **Node-count propagation across shared edges is the thing MSES explicitly overrides in the
   slot.** Its generator fudges the two facing surfaces' distributions to match, and warns that
   not doing so causes "massive grid shearing". A declared topology that lets two facing walls
   carry independent spacing laws across a few-percent-chord gap is choosing the failure MSES
   designs around.
5. **The one thing worth not reading into this**: O-versus-C is worth about 5% in drag polar on
   a NACA 0015 (Chan et al., Fig. 21), and the modern NASA 2-D three-element system uses
   **O-grids** for the two elements with the strongest wake interaction. A 14% improvement in
   *mean* non-orthogonality bought with a fold is, on that evidence, not obviously a trade worth
   making.

## Gaps I could not close, by name

1. **NASA's TMR has no 30P30N page.** The brief asked for "the 30P30N and multi-element pages".
   The only multi-element case on the TMR is **VERIF/2DMEA**, a 2-D kink cut of the CRM-HL. I
   checked the site's own source repository listing (`TMBWG/turbmodels`, 462 top-level entries):
   the only multi-element artefacts are `multielementverif.html`,
   `multielementverif_grids.html`, `multielementverif_saneg.html`,
   `multielementverif_sanegrc.html` and the two grid directories. The string `30P30N` does not
   occur on the TMR index page. 30P30N lives in the **BANC** workshop series instead. **[V]**
2. **The LAVA 2-D 30P30N grids themselves were not downloaded or inspected.** The TMR hosts
   `2D_HL-CRM_LAVA_structured_grids.tar.gz` (part of a 174 MB bundle). Opening it would turn
   several **[I]**s in §3 into measurements — the actual shape of each zone's outer boundary,
   the actual overlap, the actual block corner placement. I did not do it.
3. **Rogers, Wiltberger & Kwak (AIAA 92-0405) body text.** Abstract only, via NTRS citation
   19920043634. The patched-versus-Chimera comparison's *conclusion* is therefore **[2nd]**;
   I quote only the abstract's statement that the comparison was made.
4. **Rogers, Cao & Su, "Grid generation for complex high-lift configurations", AIAA 98-3011** —
   `OVERMAGG`'s own paper, and the one document most likely to state the 2-D multi-element
   overset topology as a *rule* rather than as one case. Not located in open access.
5. **Chen & Fu, AIAA 2003-4077** — Window-Embedment's defining paper. Not located in open
   access; the technique is quoted from ICCFD7-2012-2402's three-sentence summary of it, so
   **I do not know whether the "windows" are rectangles in physical space or in the C-grid's
   computational space.** That is the single most relevant unanswered sub-question in this note
   for the rectangle question, and I could not settle it.
6. **No published block count for a TWO-element 2-D section.** Every count I found is for three
   elements or for 3-D. The brief asked for both; I can answer only one.
7. **Where singular/degenerate corners are tolerated is answered only in fragments.** I found
   three specific tolerances (§5) and no general statement — nothing saying, for instance, how
   many blocks may meet at a point in a 2-D multi-element grid, or whether 3- and 5-block
   corners are routine. GridPro's topology engine presumably has a position on this; I did not
   find it documented publicly.
8. **The ICEM multi-element blocking recipes are practitioner reports, not documentation.** The
   recurring recipe — C-grid round the main, split the wake blocks, turn one into a C round the
   flap with the O-grid tool, collapse the blocks that run to the outlet — appears on CFD Online
   threads (e.g. `cfd-online.com/Forums/ansys-meshing/223032`, `/148661`), **not** in any ANSYS
   manual I read. Marked **[2nd]** and used nowhere above as evidence.
9. **The MDPI paper "Automatic Structured Mesh Generation Method for Airfoil Configuration
   Based on Parametric Multi-Block Topology"** (doi 10.3390/app16021116) returned HTTP 403 to
   every route I tried. From its title it is the closest thing to a direct answer on parametric
   multi-block topology for airfoils, and I could not read it.
10. **Nothing here is measured in this repo.** No mesh was generated, no quality figure was
    re-derived, and §6 is reasoning from other people's sources to this repo's numbers, not a
    measurement of this repo. The 23× area ratio and the 14% non-orthogonality figure are the
    brief's, quoted, not reproduced.
